# Brainstorming — 结构化的创意发散

在决定怎么做之前，先把所有可能性摊开、评估权衡、达成共识。

## 何时使用

**Use When:**
- 需要在多个方案之间做决定
- 问题有 2 个以上的合理解法
- 关键假设还没被验证（"这个方案假设用户会主动反馈，但其实未必"）
- 团队对某个决定有分歧

**Do Not Use When:**
- 已经有明确的决策权人，只等他们拍板
- 只有一个技术可行的方案（此时直接进入 `plan`）
- 用户明确说"不用讨论，就用方案 X"

## 核心流程

### 1. 澄清目标与约束

问清楚这轮决策的 **范围边界**：

- 要解决什么问题？（1 句话）
- 成功的定义是什么？（3-5 条评估标准）
- 有哪些硬约束？（时间、预算、技术栈、法规）
- 哪些假设是可以挑战的？

**示例问题：**
```
你说想加一个"推荐功能"。
这个功能的首要目标是：
(a) 让用户发现新内容
(b) 提高用户参与度
(c) 减少冷启动问题
(d) 都很重要，但优先级不同
```

不要假设目标很清楚；大多数时候它不清楚。

### 2. 发散 — 生成 2-4 个备选方案

每个方案应该：
- 在逻辑上可行（不是科幻）
- 与问题的陈述相关
- 代表不同的权衡取舍

**方案的多样性来源：**
- **技术路径**："用 ML 模型" vs "用规则引擎" vs "用用户反馈信号"
- **范围**："最小化版本（MVP）" vs "成熟版本"
- **实现位置**："前端" vs "后端" vs "混合"
- **时间维度**："今天上线（脏）" vs "3 个月打磨（精）"
- **用户体验**："显式选择" vs "隐式推荐"

对每个方案写 2-3 句话说 **为什么这个值得考虑**（不要打价值判断，只说理由）。

**示例：**
```
方案 A：基于用户过去的浏览记录 + 协同过滤
  为什么考虑：简单、可立刻实现、用现有数据
  
方案 B：让用户显式选择感兴趣的标签，然后推荐
  为什么考虑：更可控、用户能理解推荐逻辑、便于迭代
  
方案 C：组合 A + B：协同过滤 + 用户标签信号
  为什么考虑：结合两边优点，但复杂度也更高
```

### 3. 收敛 — 对每个方案评估权衡

建一个简单的评分表：

| 维度 | 方案 A | 方案 B | 方案 C | 权重 |
|------|--------|--------|--------|------|
| 实现复杂度 | 低 | 中 | 高 | 30% |
| 用户可理解性 | 中 | 高 | 中 | 25% |
| 推荐质量 | 中 | 低 | 高 | 35% |
| 时间到上线 | 1 周 | 2 周 | 4 周 | 10% |

**关键原则：**
- 列出 **真实权衡**（不是所有维度都是好）
- 权重要反映 **这个场景下** 什么最重要（不是一般情况）
- 如果某个维度本质是未知数，标记为"假设待验证"

### 4. 决策 — 选择一个方案

基于评分 + 直觉，推荐一个。说明：
- 为什么这个方案赢了（哪 2-3 个维度最关键）
- 有哪些已知的风险（诚实说）
- 什么条件下我们会改主意（反悔门槛）

**示例：**
```
推荐方案 B（用户标签 + 显式选择）。
理由：推荐质量虽然单独看不如方案 C，但用户可理解性更高、
实现也更快。用户理解的推荐比黑盒推荐更容易获得信任。
风险：如果用户根本不标签这个动作，推荐就会 degrade。
反悔点：两周后看用户标签率，如果 <10%，我们考虑加回协同过滤。
```

### 5. 验证关键假设

每个方案都隐含了假设。列出 TOP 3-5：

**示例假设：**
- "用户会主动标签自己的兴趣"
- "推荐刷新延迟 <500ms 用户才不会烦"
- "90% 用户在接触推荐后的 24h 内有反馈信号"

**验证方法（选一个）：**
- **用户访谈**：问 3-5 个目标用户 "你会不会手动标签？为什么？"
- **数据查询**：看现有用户数据里有没有类似信号（过去标签率、反馈频率）
- **低保真原型**：用 Figma/纸质模型展示给用户，看他们怎么反应
- **小范围试验**：给 1-5% 用户推，看指标

最重要的假设 **必须验证**；次要的假设可以作为后续迭代项。

## 反模式 (Anti-Patterns)

| 反模式 | 修正 |
|--------|------|
| 列出 10 个方案 | 就列 2-4 个有本质差别的；太多了反而麻痹决策 |
| 没定义成功标准就开始讨论 | 回到第 1 步，先澄清 |
| 评分表里所有指标都给某方案打满分 | 不现实；正视权衡。如果真的没权衡，那就不需要讨论这个决策 |
| 找不到想要的数据就放弃假设验证 | 换个验证方法（问人、分析现有数据、原型测试） |
| 讨论了 1 小时还没决出来 | 设定时间盒（30 分钟讨论、5 分钟决策） |

## 与 CyberClaw 对象模型的关系

这个 skill 本身是 **方法论**，不执行任何代码。真正的执行路径：

1. Agent 按照本 skill 的步骤与用户讨论（对话驱动）
2. 对话结果（目标、方案评估、最终决策）持久化到 Artifact（`cyberclaw-store`）
3. 如果需要实现该决策，走后续 skill 或直接进入 `SubAgentOrchestrator::spawn_child(...)` 派遣执行

**不要：**
- 让 Skill 本体去跑代码或脚本
- 跳过讨论直接决策
- 用 brainstorming 代替 code review（这是两回事）

## 关键原则（重复以强化）

1. **从目标开始，不从方案开始** — 很多人跳过目标澄清，直接讨论技术。结果往往是答非所问。
2. **权衡是真实的** — 如果某个方案在所有维度都赢了，那就不需要讨论，直接用那个。真正的决策都伴随权衡。
3. **验证假设 > 打辩论赛** — 有分歧时，不是比谁嘴更硬，而是问 "我们怎么查"。
4. **时间盒** — brainstorming 可以陷入无限讨论。设定时间（30 分钟讨论、5 分钟决策、10 分钟假设验证计划）。
5. **文档化决策** — 写下选了哪个方案、为什么、反悔条件。后来的人不需要猜你是怎么想的。

## 输出格式

讨论完成后，整理成以下结构保存到 Artifact：

```
# Brainstorming Report: [Topic]

## 目标与约束
- 问题陈述：...
- 成功标准：...
- 硬约束：...

## 备选方案 (2-4 个)
### 方案 A: [名字]
  描述 / 理由 / 已知风险

### 方案 B: [名字]
  ...

## 权衡评分表
[表格]

## 最终决策
推荐：方案 [X]
理由：...
风险：...
反悔条件：...

## 关键假设 + 验证计划
1. 假设：...
   验证方法：...
   优先级：[HIGH/MEDIUM/LOW]
```

这份 report 可以用来：
- 向利益相关者解释决策逻辑
- 作为后续实现的 context（`plan` skill 或 `Execution`）
- 在后续迭代时回顾 "当时我们为什么这样选"
