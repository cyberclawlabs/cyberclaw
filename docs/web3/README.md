# Web3 Guide

CyberClaw 是通用可治理 Agent 平台，Web3 是当前最强的落地场景。

## 为什么 Web3 是主场景

Web3 比很多普通自动化环境更早暴露平台边界问题：

- 风险动作不可逆
- 签名与权限边界更敏感
- 多系统协作更复杂
- 审计与追踪要求更高

这正是 CyberClaw 的价值所在：把风险感知、审批策略、审计追踪和多步骤执行组织成一条治理链。

## 核心场景示例

CyberClaw 在 Web3 方向最适合承载的不是“一个会聊币圈的助手”，而是高风险工作流底座，例如：

- 金库 / 多签执行前的上下文汇总、风险检查、审批链路与执行留痕
- 钱包与 signer 参与的链上 runbook，把策略、执行和审计拆开
- 协议治理与运营协同，把链上动作、外部系统、内部审批统一进一条治理链
- 链上异常处置，把告警、升级、记录、后续操作组织成受控流程

## 典型治理链路

下面这些例子更接近 CyberClaw 在 Web3 中应承担的角色：

| 场景 | 示例链路 |
|------|------|
| 金库 / 多签操作 | `Agent` 汇总钱包余额、待处理申请、链上上下文和策略条件；`Skill` 形成执行提案；治理链做审批和策略判断；钱包 `Connector` 只执行被允许的 `Capability`；系统留下审批记录、交易相关产物和执行追踪。 |
| Signer 参与的链上 runbook | `Agent` 先识别协议状态或市场触发条件；`Skill` 生成分步骤 runbook；治理链限制哪些动作可以继续；链上 `Connector` 在受控预算和权限边界内执行；平台沉淀操作前后的审计证据。 |
| 协议运营协同 | `Agent` 把链上事件、治理提案、风险数据和外部协作系统统一到一个流程里；GitHub、Slack、数据库和链上系统分别通过 `Connector` 接入；审批、升级和执行都沿统一治理链运行。 |
| 链上安全事件处置 | `Agent` 接收告警后先拉取追踪、交易上下文和相关证据，再提出下一步动作；治理链决定是否允许冻结流程、升级人工处理或触发后续 runbook；每一步都留下可追溯记录。 |

## 更具体的团队用法

如果你要把它理解成团队里的真实工作，而不是抽象平台，可以先看这些例子：

- 金库操作前检查：
  `Agent` 汇总多签请求、钱包余额、白名单策略和待执行上下文，输出一份可审批提案，而不是直接发交易。
- Signer 参与的执行门禁：
  `Agent` 可以准备执行参数、风险摘要和回滚建议，但真正进入 signer 或钱包执行面之前，必须经过治理链。
- 协议治理提案协同：
  `Agent` 收集治理提案、链上数据、风险备注和外部协作文档，再通过 GitHub / Slack / 数据库等接入面组织评审和执行准备。
- 链上异常分诊：
  `Agent` 接收异常交易、告警或链上状态变化后，先做上下文聚合、影响评估和升级建议，再决定是否进入后续处置流程。
